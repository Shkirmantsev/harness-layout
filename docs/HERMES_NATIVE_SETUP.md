# Native Hermes integration

## Contract

The final design uses two client-specific ingress paths and one native Hermes execution path:

```text
Claude Code -> remote MCP sidecar -> native Hermes /v1/runs
OpenCode    -> native Hermes `/v1/runs` API directly through project-local `hermes_*` tools
Hermes      -> native SSH backend -> dedicated main-PC user -> PROJECT_ROOT
```

The MCP sidecar is **not** a filesystem bridge. It accepts a `project_root` plus a task and controls Hermes run lifecycle. Hermes itself reads, edits, searches, tests, and analyzes repository media.

Codex has no Hermes transport in this phase.

## Main-PC project boundary

`make hermes-host-setup` creates/reuses `HERMES_PROJECT_USER` (default `hermes-worker`):

- no sudo/docker/adm/lxd membership;
- locked password;
- traverse-only ACL on parent directories;
- `rwX` ACL on the exact `PROJECT_ROOT`;
- default project ACL for newly-created files;
- explicit denial for currently-present paths matching `HERMES_PROJECT_DENY_GLOBS`;
- no `/workspace` symlink;
- no dedicated SSH keypair generated by the harness.

Because this is a normal Linux account rather than a VM sandbox, world-readable OS files may still be visible. Use a dedicated VM if that is unacceptable for your enterprise threat model.

## Tailscale SSH

Recommended to avoid SSH key management:

```bash
make hermes-host-setup ENABLE_TAILSCALE_SSH=1
```

Hermes' SSH environment uses non-interactive `BatchMode=yes`. Configure the tailnet SSH policy narrowly enough to permit the remote Hermes node to connect as `HERMES_PROJECT_USER` without an interactive re-authentication step. Do not open SSH to the public Internet as a workaround.

## Remote host

After `.env` is configured:

```bash
make hermes-sidecar-copy
make hermes-remote-instructions
```

`make hermes-sidecar-copy` transfers only the sidecar source under `remote/hermes-worker-mcp/`; no secret is copied.

`make hermes-remote-instructions` renders `.generated/HERMES_REMOTE_SETUP.md`, which tells the remote Hermes/operator to:

1. back up the existing worker profile;
2. require Hermes >=0.20.5;
3. preserve the existing native OpenAI API/provider/SOUL/memory;
4. configure `terminal.backend: ssh` with reusable `cwd: "~"`;
5. prove native access to the current absolute repository path;
6. install the separate Claude-only MCP sidecar on the remote host;
7. verify native file and vision behavior;
8. remove obsolete project/session/attachment bridges only after native access passes.

## Claude Code

`make client-config` generates `.claude/agents/generated-hermes-worker.md` (gitignored, mode 0600). It contains an inline MCP connection to:

```text
HERMES_REMOTE_HOST:HERMES_REMOTE_SIDECAR_PORT/mcp
```

with the sidecar bearer token. The dispatcher passes `PROJECT_ROOT` to `hermes_run`; it does not upload project files.

## OpenCode

`make client-config` generates `.opencode/tools/hermes.js` plus `.generated/opencode-hermes-runtime.json`. OpenCode does **not** create a Hermes model provider or `@generated-hermes` subagent.

The normal OpenCode main model (for example MiniMax) delegates by calling project-local tools:

```text
hermes_delegate -> POST HERMES_REMOTE_HOST:HERMES_REMOTE_OPENAI_PORT/v1/runs
hermes_wait/status/result -> GET /v1/runs/{run_id}
hermes_steer/approve/cancel -> native run-control endpoints
```

The tool injects the absolute authorized project root into Hermes run instructions. Hermes then reads/edits/tests through its own SSH-backed tools. No Hermes MCP is added to OpenCode.

## Images and other files

For repository images, tell Hermes the path in the project. Hermes 0.20.5+ resolves local image paths through a non-local backend and reads bytes inside the SSH environment. This avoids a custom attachment relay.

For a text-only main model, a working `auxiliary.vision` route is still required for image understanding.

PDFs and other files are accessed normally over SSH. Stage an external file with:

```bash
make hermes-import FILE=/path/to/file.pdf
```
